# Decisions

Dated log of product and engineering decisions. Add new entries at the bottom. When a decision is replaced, keep the old entry and mark it "Replaced by #N".

| # | Date | Decision | Why |
| --- | --- | --- | --- |
| 1 | 2026-11-08 | The project is named `shadowarmy`. | Plain English, free on npm at the time of checking, fits "an army that grows on command". `strawhats` was rejected because it is a specific trademarked franchise name. |
| 2 | 2026-11-08 | Role names: Monarch (human), Marshal, Soldier, Knight, Scout, Sentinel; the control repository is the Realm. Labels and docs stay plain. | Themed but generic words; no character names or artwork from any franchise. |
| 3 | 2026-11-08 | Build a standalone project inspired by firstmate instead of adding a GitHub Actions runtime to firstmate. | firstmate's core is a live supervisor driving interactive terminal sessions; Actions runs are not interactive. A small, separate upstream contribution (GitHub Issues backlog) is planned instead. See [firstmate bridge](firstmate-bridge.md). |
| 4 | 2026-11-08 | All agent machinery lives in a separate Realm repository; target repositories stay clean. | Users asked that built projects contain no agent details. Mirrors firstmate's separate home. |
| 5 | 2026-11-08 | Realms are created by `init` from a `template/` folder and call the engine's reusable workflows at a pinned major version, instead of forking the engine. | Forks of public repositories cannot be private and have Actions disabled by default; reusable workflows let every Realm receive fixes by version. |
| 6 | 2026-11-08 | Agents are Claude Code run headless in workflow steps; git, pushes, pull requests and labels are deterministic scripts. `anthropics/claude-code-action` is not the core runtime. | Cross-repository work and exact state handling need deterministic control, and the agent step must not hold the GitHub write token. The action is built around acting on the triggering repository. Revisit if it gains a suitable mode. |
| 7 | 2026-11-08 | All state lives on GitHub: one state label per issue plus one engine-authored status comment with a schema-validated state block. | Survives any run dying; visible from the GitHub mobile app; no service to host. |
| 8 | 2026-11-08 | Target repository events are observed by a scheduled Sentinel, not by workflows inside target repositories. | Keeps targets clean. Cost: reactions take minutes. |
| 9 | 2026-11-08 | No automatic merging, ever. | The Monarch is the only authority over what lands. |
| 10 | 2026-11-08 | Engine scripts are TypeScript on Node 22. | The CLI ships through npm, so Node is required anyway; one language for scripts and CLI. |
| 11 | 2026-11-08 | Users bring their own Claude credential and GitHub token; no hosted shadowarmy service. | Ownership, cost and trust: no server holding write access to other people's code. |
| 12 | 2026-11-08 | TypeScript runs directly on Node's built-in type stripping (Node 22.18 or later) for tests and dev scripts; `tsc` only type-checks and builds `dist/`. Source uses only erasable syntax and `.ts` import extensions. | No `tsx`, `ts-node` or bundler to maintain; tests run the exact source files. |
| 13 | 2026-11-08 | JSON Schemas live in `src/schemas/` as TypeScript modules and are validated with Ajv. Schemas are typed with Ajv's `JSONSchemaType` where it can express them; the state block schema cannot be (required keys that may be null), so tests keep it in step with its type. Defaults live in code (`src/config.ts`), not in the schema. | One validator for config and every agent output; schemas can be given to agents verbatim; typed defaults without casts. |
| 14 | 2026-11-08 | Transition table amended: any non-final state (including a fresh `arise` order) may move to `failed`, and `needs-decision` may move to `planning`. | Resolves contradictions inside the contract: section 11 says any step failure moves to `failed` and the single-task sequence moves a fresh order to `failed` on bad config, but the table did not list those; section 12 reruns the Marshal after `/answer`. |
| 15 | 2026-11-08 | The state block (version 1) has the fields of the data model in the architecture diagram (`kind`, `base`, `parent`, `dependsOn` added to the behavior contract's list); every field is required and may be `null` where not applicable. | The two documents disagreed; the larger set is needed for multi-task orders and New project orders, and requiring every field avoids guessing defaults when reading. |
| 16 | 2026-11-08 | Engine CI fails on any `${{ }}` expression inside a `run:` script, not only `github.event` ones. | Inputs, branch names and step outputs can carry untrusted text too; one simple rule is easier to keep than a list of unsafe contexts. |
| 17 | 2026-11-08 | Branch names from orders (`base`) are limited to letters, digits, `.`, `_`, `/`, `+` and `-` on top of git's own rules. | Git accepts `;`, `$` and quotes in branch names; nothing legitimate needs them and they are risky wherever a value meets a shell. |
| 18 | 2026-11-08 | Transition table amended again: `in-progress` may move to `ready-to-merge` (milestone 1 only, removed in milestone 2), `planning` may move to `in-progress` or `queued`, and `failed` may move to `planning`. A multi-task order's own state is derived by the Sentinel and written with the label writer's derived mode, which skips the table but keeps the single-state writer and never leaves a final state. | Decision 14 missed these paths. The milestone 1 single-task sequence ([single-task order](../functional-diagrams/actions/single-task-order.md)) and the roadmap move an order from `in-progress` straight to `ready-to-merge` because there is no Knight yet. The plan approval and dispatch sequence ([plan approval and dispatch](../functional-diagrams/actions/plan-approval-and-dispatch.md)) dispatches a single-task plan without approval from `planning` to `in-progress` or `queued`. `/retry` after a Marshal failure (section 11) restarts planning. The derived order states of section 4 move between `in-progress`, `needs-decision`, `ready-to-merge` and `done` in orders no step-by-step table can list. |
