# Decisions

Dated log of product and engineering decisions. Add new entries at the bottom. When a decision is replaced, keep the old entry and mark it "Replaced by #N".

| # | Date | Decision | Why |
| --- | --- | --- | --- |
| 1 | 2026-11-08 | The project is named `shadowarmy`. | Plain English, free on npm at the time of checking, fits "an army that grows on command". `strawhats` was rejected because it is a specific trademarked franchise name. |
| 2 | 2026-11-08 | Role names: Monarch (human), Marshal, Soldier, Knight, Scout, Sentinel; the control repository is the Realm. Labels and docs stay plain. | Themed but generic words; no character names or artwork from any franchise. |
| 3 | 2026-11-08 | Build a standalone project inspired by firstmate instead of adding a GitHub Actions runtime to firstmate. | firstmate's core is a live supervisor driving interactive terminal sessions; Actions runs are not interactive. A small, separate upstream contribution (GitHub Issues backlog) is planned instead. See [firstmate bridge](firstmate-bridge.md). |
| 4 | 2026-11-08 | All agent machinery lives in a separate Realm repository; target repositories stay clean. | Users asked that built projects contain no agent details. Mirrors firstmate's separate home. |
| 5 | 2026-11-08 | Realms are created by `init` from a `template/` folder and call the engine's reusable workflows at a pinned major version, instead of forking the engine. | Forks of public repositories cannot be private and have Actions disabled by default; reusable workflows let every Realm receive fixes by version. |
| 6 | 2026-11-08 | Agents are Claude Code run headless in workflow steps; git, pushes, pull requests and labels are deterministic scripts. `anthropics/claude-code-action` is not the core runtime. | Cross-repository work and exact state handling need deterministic control, and the agent step must not hold the GitHub write token. The action is built around acting on the triggering repository. Revisit if it gains a suitable mode. |
| 7 | 2026-11-08 | All state lives on GitHub: one state label per issue plus one engine-authored status comment with a schema-validated state block. | Survives any run dying; visible from the GitHub mobile app; no service to host. |
| 8 | 2026-11-08 | Target repository events are observed by a scheduled Sentinel, not by workflows inside target repositories. | Keeps targets clean. Cost: reactions take minutes. |
| 9 | 2026-11-08 | No automatic merging, ever. | The Monarch is the only authority over what lands. |
| 10 | 2026-11-08 | Engine scripts are TypeScript on Node 22. | The CLI ships through npm, so Node is required anyway; one language for scripts and CLI. |
| 11 | 2026-11-08 | Users bring their own Claude credential and GitHub token; no hosted shadowarmy service. | Ownership, cost and trust: no server holding write access to other people's code. |
| 12 | 2026-11-08 | TypeScript runs directly on Node's built-in type stripping (Node 22.18 or later) for tests and dev scripts; `tsc` only type-checks and builds `dist/`. Source uses only erasable syntax and `.ts` import extensions. | No `tsx`, `ts-node` or bundler to maintain; tests run the exact source files. |
| 13 | 2026-11-08 | JSON Schemas live in `src/schemas/` as TypeScript modules and are validated with Ajv. Schemas are typed with Ajv's `JSONSchemaType` where it can express them; the state block schema cannot be (required keys that may be null), so tests keep it in step with its type. Defaults live in code (`src/config.ts`), not in the schema. | One validator for config and every agent output; schemas can be given to agents verbatim; typed defaults without casts. |
| 14 | 2026-11-08 | Transition table amended: any non-final state (including a fresh `arise` order) may move to `failed`, and `needs-decision` may move to `planning`. | Resolves contradictions inside the contract: section 11 says any step failure moves to `failed` and the single-task sequence moves a fresh order to `failed` on bad config, but the table did not list those; section 12 reruns the Marshal after `/answer`. |
| 15 | 2026-11-08 | The state block (version 1) has the fields of the data model in the architecture diagram (`kind`, `base`, `parent`, `dependsOn` added to the behavior contract's list); every field is required and may be `null` where not applicable. | The two documents disagreed; the larger set is needed for multi-task orders and New project orders, and requiring every field avoids guessing defaults when reading. |
| 16 | 2026-11-08 | Engine CI fails on any `${{ }}` expression inside a `run:` script, not only `github.event` ones. | Inputs, branch names and step outputs can carry untrusted text too; one simple rule is easier to keep than a list of unsafe contexts. |
| 17 | 2026-11-08 | Branch names from orders (`base`) are limited to letters, digits, `.`, `_`, `/`, `+` and `-` on top of git's own rules. | Git accepts `;`, `$` and quotes in branch names; nothing legitimate needs them and they are risky wherever a value meets a shell. |
| 18 | 2026-11-08 | Transition table amended again: `in-progress` may move to `ready-to-merge` (milestone 1 only, removed in milestone 2), `planning` may move to `in-progress` or `queued`, and `failed` may move to `planning`. A multi-task order's own state is derived by the Sentinel and written with the label writer's derived mode, which skips the table but keeps the single-state writer and never leaves a final state. | Decision 14 missed these paths. The milestone 1 single-task sequence ([single-task order](../functional-diagrams/actions/single-task-order.md)) and the roadmap move an order from `in-progress` straight to `ready-to-merge` because there is no Knight yet. The plan approval and dispatch sequence ([plan approval and dispatch](../functional-diagrams/actions/plan-approval-and-dispatch.md)) dispatches a single-task plan without approval from `planning` to `in-progress` or `queued`. `/retry` after a Marshal failure (section 11) restarts planning. The derived order states of section 4 move between `in-progress`, `needs-decision`, `ready-to-merge` and `done` in orders no step-by-step table can list. |
| 19 | 2026-11-09 | Monarch `/answer` texts are not copied into the state block. `answers.md` is assembled from the issue's `/answer` comments whose author is the configured Monarch, oldest first, when an agent run is assembled. | The comments are already durable records on GitHub, and copying them into the state block would compete with the status comment's 65536-character budget. |
| 20 | 2026-11-09 | Spike: the Soldier runs as `claude --safe-mode -p <prompt> --model <m> --max-turns <n> --output-format json --dangerously-skip-permissions --no-session-persistence`, with Claude Code pinned (2.1.319, `CLAUDE_CODE_VERSION` in `order.yml`). `--max-turns` works but is hidden from `--help`. | `--safe-mode` stops the target repository's `CLAUDE.md`, hooks, MCP servers, skills and plugins from loading, so repository content stays data, while authentication still works. `--bare` does the same but only accepts `ANTHROPIC_API_KEY`, which would rule out the subscription credential. |
| 21 | 2026-11-09 | Spike: both Claude credentials are supported; `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` is the documented default and `ANTHROPIC_API_KEY` the alternative. The Monarch should use a credential dedicated to the Realm. | `claude setup-token` exists to create long-lived tokens for non-interactive use such as CI on the user's own repositories. A dedicated credential can be revoked without affecting the Monarch's other use. |
| 22 | 2026-11-09 | Spike: the reusable workflow checks out the engine with `repository: ${{ job.workflow_repository }}` and `ref: ${{ job.workflow_sha }}`, not an `engine_ref` input. | GitHub's `job` context names the repository and commit of the workflow file that defines the job, so the scripts always match the workflow version the Realm called, with nothing for the caller to keep in sync. |
| 23 | 2026-11-09 | The order workflow uses separate jobs: `gate` (Realm token, plus `SHADOWARMY_GH_TOKEN` in its Gate step only, to fetch the target and pack it into the Soldier inputs), `soldier` (agent; only the Claude credential, `permissions: {}`), `deliver` (Realm token and `SHADOWARMY_GH_TOKEN`) and `report-failure`. `SHADOWARMY_GH_TOKEN` never reaches the soldier job, and the base commit comes from the gate job's outputs. Everything the soldier job produces (`result.json`, the patch) is treated as untrusted and re-checked in `deliver` on a fresh runner, where the patch is applied to a fresh fetch of the base commit. | Within one job, a process the agent leaves running could read later steps' environment, including the write token, from `/proc`. And any secret a job references is sent to its runner process, which the passwordless `sudo` of hosted runners lets the agent read from memory. Separate jobs run on separate runners, and the agent's job is never sent the write token. |
| 24 | 2026-11-09 | Test Realms can set the repository variable `SHADOWARMY_FAKE_AGENT` to a scenario in `scripts/fake-agent.sh` (`add-file`, `edit-claude-md`, `no-changes`, `blocked`, `invalid-result`) to replace the Soldier with a canned script. The gate rejects unknown values. | End-to-end tests of the deterministic pipeline (diff guard, push, pull request, labels) must be repeatable, which a real agent that follows its prompt is not. Anyone who can set Realm variables can already change the Realm's workflows. |
| 25 | 2026-11-09 | Until the first release (milestone 5), the template's caller workflow uses the engine at `@main`; the engine repository is public. | No `v1` tag exists yet, and a private engine cannot be called from other repositories without extra access settings. |
| 26 | 2026-11-09 | Re-running an order replaces its own task branch only with `--force-with-lease` against the commit seen moments before, and reuses the open pull request for that branch. In milestone 1, re-adding `arise` is the way to retry a `failed` order and to continue after `needs-decision` (the Monarch edits the task first); `/retry` and `/answer` arrive in milestone 3. | The engine created the branch, so replacing it is not rewriting someone else's work, and the lease prevents clobbering a concurrent change. |
| 27 | 2026-11-09 | In pull request bodies the Realm issue number is written as `` `#N` `` unless the Realm issue is linked. | A bare `#N` in a target repository links to that repository's own issue N, which would be wrong and confusing. |
| 28 | 2026-11-09 | The daily run cap counts jobs named after an agent role (`soldier`, later `marshal`, `knight`, `scout`) that started and were not skipped, in the Realm's workflow runs created since 00:00 in `timezone`. | It uses only GitHub's own run history, so nothing extra is stored, and it matches the contract's definition of a run (a job that starts an agent). |
| 29 | 2026-11-09 | A public Realm cannot order changes to a private target repository: the gate reads both visibilities before fetching the target and fails the order at step "check target" if the Realm is public and the target private. Workflow artifacts (`soldier-input`, `soldier-output`) are kept for 1 day. | Anyone can download the workflow artifacts of a public repository, and the order workflow hands the target checkout, the patch and the agent summary between jobs as artifacts, so a public Realm would expose a private target's source. The jobs that read the artifacts run in the same workflow run, so 1 day is enough. |
| 30 | 2026-11-09 | One workflow run is one round: gate, soldier, deliver, knight, judge. A fix round is a new run of the Realm's order workflow, started by the judge job with `workflow_dispatch` (issue number as the only input) and queued behind the current run by the per-issue concurrency group. The fix round's gate rebuilds `feedback.md` from GitHub: the Knight's latest review of the pull request's head commit (read from a machine block in the posted review) and the failed checks of that commit with log excerpts. | Jobs cannot loop, and an agent must never share a job with the write token, so the loop has to cross runs. Rebuilding the feedback from the pull request keeps all state on GitHub: a fix round needs nothing from the run that requested it, which also lets `/retry` (milestone 3) resume from the same place. |
| 31 | 2026-11-09 | The Knight runs in its own job like the Soldier (only the Claude credential, `permissions: {}`, a packed checkout of the pushed branch and the full diff from the first round's base commit). A deterministic `judge` job validates `review.json`, posts it as a comment-type pull request review with a machine block, and decides. A review only counts as the Knight's when its block is valid, it was posted by the account behind `SHADOWARMY_GH_TOKEN` and it reviews the pull request's current head commit. | Same isolation as decision 23 for the second agent. Comment-type reviews never satisfy branch protection. The author and commit checks stop other people's reviews and stale reviews from steering a fix round. |
| 32 | 2026-11-09 | The state block gains `baseSha` (the commit the first round started from), still version 1. | The Knight must review the whole change across rounds; the base branch can move, so its commit is recorded. The engine is unreleased, so version 1 can still change; existing sandbox comments are replaced on the next run. |
| 33 | 2026-11-09 | Target CI: every completed check run or commit status that did not pass (anything but success, neutral or skipped) counts as failing, because the engine cannot read which checks branch protection requires without admin access. With no check at all after 2 minutes the target counts as having no CI. Until the Sentinel exists (milestone 3) the judge waits in its job for up to `ci.max_wait_minutes`, capped at 300 minutes by GitHub's 6-hour job limit, then moves the order to `needs-decision`. | Safer to fix or ask about an optional failing check than to ignore a required one. The roadmap asks for the in-job wait until the Sentinel can take over. |
| 34 | 2026-11-09 | The daily run cap is checked only when an order starts (`arise`), not before its fix rounds. Each round counts two agent runs (Soldier and Knight). | The contract lets work in progress continue to its next safe point; fix rounds are bounded by `limits.max_fix_rounds`. |
| 35 | 2026-11-09 | Fake agent scenarios play only the first round and hand fix rounds to the real Soldier (the script exits 3); `stubborn-bug` plays every round so the round limit can be tested. New scenarios `seed-bug` and `stubborn-bug` write a known bug. The Knight is never faked, so a Claude credential is required even in test mode. | Acceptance asks that a seeded bug is found by the Knight and fixed in a later round, which needs a real Knight and a real fixing Soldier, but a deterministic bug. |
| 36 | 2026-11-09 | The Realm's caller workflow also triggers on `workflow_dispatch` with an `issue` input and grants `actions: write`; its concurrency group is keyed on the issue for both triggers. A dispatched run only does work when the sender is `github-actions[bot]` (the engine) and the order is `in-progress` with a pull request and at least one fix round recorded. Amended 2026-11-09: a dispatch by the Monarch changes nothing either, and the caller's job filter lets only dispatches by `github-actions[bot]` into the concurrency group; `/retry` (milestone 3) is the manual path. | The judge needs `actions: write` to dispatch. Collaborators with write access can dispatch workflows too; the sender and state checks make such a dispatch change nothing. A manual dispatch is an extra way in, and inside the concurrency group it would cancel the engine's pending fix-round run. |
| 37 | 2026-11-09 | The Knight reviews before the CI wait, so it does not receive CI results; failing CI reaches the Soldier directly as fix-round feedback. | Waiting for CI before the review would hold a runner for the CI wait twice per round without improving the Knight's independent code review. |
